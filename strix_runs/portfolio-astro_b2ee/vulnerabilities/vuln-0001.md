# CVE-2026-92708: devalue 5.9.2 process memory disclosure via typed-array serialization (transitive via astro)

**ID:** vuln-0001
**Severity:** LOW
**Found:** 2026-10-14 22:05:54 UTC
**Target:** portfolio-astro
**Package:** devalue
**Ecosystem:** npm
**Installed Version:** 5.9.2
**Fixed Version:** 5.9.3
**Introduced By:** astro@7.3.2
**Dependency Chain:** astro@7.3.2 > devalue@5.9.2
**CVE:** CVE-2026-92708
**CWE:** CWE-201
**CVSS:** 1.9
**Advisory CVSS:** 7.5
**Contextual CVSS Vector:** CVSS:3.1/AV:L/AC:H/PR:H/UI:N/S:U/C:L/I:N/A:N
**Fix Effort:** Low

## Description

The dependency tree pinned by `bun.lock` contains **devalue 5.9.2**, which is affected by **CVE-2026-92708** (published advisory CVSS 7.5 HIGH): `stringify`/`uneval` serialize a typed array by emitting its entire backing `ArrayBuffer`, so serializing a Node `Buffer` (backing store is a process-wide shared pool) discloses up to 64 KB of unrelated process memory into the serialized output. Fixed in **5.9.3**. devalue is a transitive dependency pulled in by `astro@7.3.2` (`bun.lock:612`, dependency `"devalue": "^5.8.1"`; pinned at `bun.lock:778`). In this repository the exposure is minimal: the site is a fully prerendered static Astro build with no SSR server, and no project- or CMS-controlled data reaches the vulnerable typed-array serialization path.

## Evidence

**Advisory evidence:** `CVE-2026-92708` applies to `devalue` at installed version `5.9.2`. The advisory is fixed in `5.9.3`.

**Transitive dependency:** introduced by the direct dependency `astro@7.3.2`.

**Dependency chain:** `astro@7.3.2 > devalue@5.9.2`

**Usage analysis:** imported by application code; affected API usage unconfirmed. devalue is not imported by application code (no `devalue` reference anywhere under `src/`); it enters only through the direct dependency `astro@7.3.2` (package.json:26, bun.lock:612 requires `"devalue": "^5.8.1"`, pin at bun.lock:778), which is used on every build (`bun run build`). The vulnerable symbols (stringify/uneval typed-array serialization) appear in astro's dist consumers at node_modules/astro/dist/content/{vite-plugin-content-imports.js,data-store.js,data-store-writer.js,mutable-data-store.js}, node_modules/astro/dist/actions/runtime/{server.js,client.js}, and node_modules/astro/dist/core/session/runtime.js — but none of those subsystems are active in this project: no src/content/ directory exists, the build output is fully static (no server actions, no sessions), and the two client:load islands (src/layouts/BaseLayout.astro:80, src/components/base/Header.astro:39,45) serialize literal empty props (`props="{}"` in dist/index.html). The specific vulnerable behavior (serializing a Node Buffer/typed array) is never exercised with any data, attacker- or operator-controlled, and no devalue runtime ships in dist/_astro/*.js. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

Build-process memory disclosure: if a Node Buffer or typed array were passed through devalue serialization during `astro build`, up to 64 KB of build-process memory (potentially including build env such as `CONTENT_API_KEY`/`GHOST_URL` set in the Docker build stage) would be emitted into published static output. In this codebase no Buffer/typed-array data is serialized and no long-running multi-request SSR process exists, so no disclosure was demonstrated; the pinned version nonetheless keeps the vulnerable code in the build toolchain.

## Technical Analysis

**Version verification.** `bun.lock:778` pins `devalue@5.9.2`; the advisory affects 5.1.0–5.9.2 and fixes 5.9.3, so the pin is in the affected range. Trivy (vuln DB refreshed at scan time, 2026-10-14) matched it from `bun.lock`.

**Source-to-sink trace (this codebase).**
- Entry point: lockfile pin `bun.lock:778` + direct dependency `astro: ^7.3.2` at `package.json:26`; astro requires `"devalue": "^5.8.1"` (`bun.lock:612`).
- Usage sites of devalue inside astro 7.3.2 (`node_modules/astro/dist`): `content/vite-plugin-content-imports.js`, `content/data-store.js`, `content/data-store-writer.js`, `content/mutable-data-store.js` (content collections), `actions/runtime/server.js` + `actions/runtime/client.js` (server actions), `core/session/runtime.js` (sessions), `core/errors/errors-data.js`. 
- None of these paths are active in this project: there is no `src/content/` directory (no content collections — blog content is fetched at build time via `@tryghost/content-api` in `src/lib/ghost.ts:14`), no server actions (output is fully static), and no Astro session usage.
- The only hydrated islands are `DarkModeToggle` and `FxToggle` with `client:load` and no props (`src/layouts/BaseLayout.astro:80`, `src/components/base/Header.astro:39,45`); the built HTML carries literal `props="{}"` (verified in `dist/index.html`), so no devalue-serialized payload — typed array or otherwise — is produced or shipped. No `devalue` markers were found in any `dist/_astro/*.js` client bundle.
- The CVE's canonical scenario (SvelteKit/Nuxt-style SSR where a public `load()` returns a small Buffer, disclosed across in-flight requests in a long-running process) requires a multi-request server, which this static nginx deployment does not have.

**Counterevidence pass.** Checked: all astro dist consumers of devalue (listed above), all project source imports (no `devalue` import anywhere in `src/`), island props in built output (`{}`), client bundles (no devalue parse runtime shipped), and absence of SSR. The only remaining theoretical trigger is an operator placing a Buffer/typed array into island or content-collection props — a developer-position action, not an attacker path.

**Environment caveat.** External advisory lookup (web search) was unavailable in this scan; verification relies on the Trivy vulnerability database downloaded fresh from `mirror.gcr.io/aquasec/trivy-db:2` at scan time plus its embedded advisory references (GHSA-j22f-vq7h-c4qm, sveltejs/devalue commit 46dc877b).

## Contextual CVSS

The published 7.5 (AV:N/PR:N/C:H) rates devalue inside a long-running internet-facing SSR framework where a public page returns a Buffer. This codebase proves that position does not exist: the entry point is the lockfile pin (bun.lock:778) consumed by the operator-invoked static build (`bun run build` in the Dockerfile build stage), astro's devalue call sites are limited to content collections/actions/sessions (node_modules/astro/dist/content/*, actions/runtime/*, core/session/runtime.js) — none activated here (no src/content/, static output) — and the only island props are literal `{}` (dist/index.html), so no Buffer/typed-array ever reaches `devalue.stringify`. A network attacker has no request path into this code at all; the residual trigger would require a developer (or someone who can already commit code) to pass a Buffer through island/content props, at which point up to 64 KB of build-process memory could land in published HTML — hence confidentiality limited to L, attack vector local, privileges required high, and integrity/availability none.

## Remediation

Refresh the lockfile so the transitive resolution moves devalue to the fixed release: run `bun update devalue` (astro's range `^5.8.1` accepts 5.9.3, so no manifest change is required). If a future astro release re-pins or the resolution stays stale, add a root-level `overrides` entry pinning `devalue` to `^5.9.3` in package.json. Also apply the sibling fixes bundled in devalue 5.9.3 (six GHSA-only advisories covering uneval expansion, ArrayBuffer-reviver validation, unhandled stringifyAsync rejection, `__proto__` key coercion, and sparse-array amplification — not separately filed because they have no CVE IDs). Re-run `bun run build` and confirm the lockfile records `devalue@5.9.3`.

The build was not re-executed for this task.
