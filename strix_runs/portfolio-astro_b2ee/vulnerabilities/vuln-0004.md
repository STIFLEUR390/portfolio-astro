## Description

The `bun.lock` tree pins **source-map-js 1.2.1**, affected by **CVE-2026-93749** (published advisory CVSS 7.5 HIGH): the library fails to validate the per-section offset line value in indexed source maps, so an attacker-supplied map with extremely large offset values causes synchronous event-loop blocking (denial of service). Versions through 1.2.1 are affected; the fix is 1.2.2. The package is a transitive build-tool dependency reached through several roots — primarily `astro@7.3.2 > vite@8.3.0 > postcss@8.5.28 > source-map-js@1.2.1` (`bun.lock:612`, `bun.lock:1238`, `bun.lock:1070`, pin at `bun.lock:1146`), and also via `tailwindcss`/`@tailwindcss/node` (bun.lock:424), `css-tree` (bun.lock:678), `magicast` (bun.lock:980), and `@vue/compiler-sfc`/`@vue/compiler-core`. This project emits no source maps and no attacker-controlled map can enter the build pipeline, so the vulnerable consumer has no reachable untrusted input here.

## Impact

Build-time denial of service on the operator's machine or CI if a malicious indexed source map were introduced into the toolchain input (e.g. committed to the repository): a `.map` file with an extreme per-section offset line value could block the build's event loop for an extended period. No confidentiality or integrity impact, and no effect on the deployed static site or its visitors — source-map-js never runs at request time, and no `.map` files are even shipped (verified: zero `*.map` files under `dist/`). Supplying the map requires write access to the repository, a trusted position.

## Technical Analysis

**Version verification.** `bun.lock:1146` pins `source-map-js@1.2.1`; the advisory covers through 1.2.1 with fix 1.2.2, so the pin is affected. Trivy (DB refreshed 2026-10-14) matched it from `bun.lock`.

**Source-to-sink trace (this codebase).**
- Entry points (lockfile → usage): `astro: ^7.3.2` (package.json:26) at bun.lock:612 pulls `vite ^8.0.13` (bun.lock:1238) → `postcss ^8.5.28` (bun.lock:1070) → `source-map-js ^1.2.1`; `@tailwindcss/vite` (package.json:21, bun.lock:424) → `tailwindcss` → `@tailwindcss/node` → `source-map-js ^1.2.1`; and the same package via `css-tree@3.2.1` (bun.lock:678), `magicast@0.5.5` (bun.lock:980), and `@vue/compiler-sfc`/`@vue/compiler-core` (vue 3.5.42 chain).
- Sink: the advisory's vulnerable consumer is the indexed-source-map section walker in `lib/source-node.js` (per-section offset line handling, commit cf76580). It runs whenever a tool parses an *indexed* `.map` file.
- Reachability in this project: none demonstrated. `astro.config.mjs` sets no `build.sourcemap`; the previously built `dist/` contains zero `*.map` files, proving the pipeline neither emits nor consumes source maps during `astro build`. The CSS pipeline (Tailwind v4 via @tailwindcss/vite) runs without sourcemap options; input CSS is developer-authored (src/styles/globals.css and scanned components). Ghost CMS content (src/lib/ghost.ts:14) is rendered into HTML via set:html and can never become a source map. The deployed site is static nginx-served files — no request-time use of this package.

**Counterevidence pass.** Confirmed no source maps exist anywhere in the build output, no sourcemap option is set anywhere in astro.config.mjs or the CSS pipeline, and the only `.map`-bearing inputs an attacker could try to introduce (a committed malicious `.map`, or a `sourceMappingURL` comment in a CSS/JS source) require repository write access — a trusted developer position already able to break the build. Nothing in the runtime deployment touches this package.

## Contextual CVSS

The published 7.5 (AV:N/PR:N/A:H) assumes an attacker can make a network-reachable service parse a malicious indexed source map. In this codebase the package exists only inside the operator's build toolchain: entry points are the direct dependency pins `astro: ^7.3.2` (package.json:26) via `astro@7.3.2 > vite@8.3.0 > postcss@8.5.28 > source-map-js@1.2.1` (bun.lock:612, 1238, 1070, 1146) and `@tailwindcss/vite`/`tailwindcss` via `@tailwindcss/node` (bun.lock:424), with additional chains through css-tree, magicast, and @vue/compiler-sfc/-core. The project emits no source maps at all (no `build.sourcemap` in astro.config.mjs and zero `*.map` files in the built dist/), so the vulnerable indexed-map consumer is never fed a map in the first place — and no attacker-controlled source map can enter the pipeline: everything the toolchain could parse is self-generated or repo-committed, and Ghost CMS content never becomes a source map. A crafted map would require commit access (a trusted developer position), so attack vector is local, privileges required high, and the demonstrated impact is build-time CPU denial only (A:L).

## Remediation

Refresh the lockfile so the transitive resolution moves to the fixed patch: run `bun update source-map-js` — every parent range accepts 1.2.2 (`postcss` and `css-tree` require `^1.2.1`), so no manifest change is needed. Verify afterward that `bun.lock` records `source-map-js@1.2.2` and that `bun run build` still succeeds. As defense in depth, never enable `build.sourcemap` in astro.config.mjs for the production deployment, and treat any third-party `.map` file added to the repository as untrusted input.
