# CVE-2026-93748: http-cache-semantics 4.2.0 cross-user cache disclosure via max-stale (transitive via astro)

**ID:** vuln-0002
**Severity:** INFO

**Target:** portfolio-astro
**Package:** http-cache-semantics
**Ecosystem:** npm
**Installed Version:** 4.2.0
**Fixed Version:** none published
**Introduced By:** astro@7.3.2
**Dependency Chain:** astro@7.3.2 > http-cache-semantics@4.2.0
**CVE:** CVE-2026-93748
**CWE:** CWE-524

**Contextual CVSS Vector:** CVSS:3.1/AV:L/AC:H/PR:H/UI:N/S:U/C:N/I:N/A:N
**Fix Effort:** Low

## Description

The `bun.lock` tree pins **http-cache-semantics 4.2.0**, affected by **CVE-2026-93748** (published advisory CVSS 7.5 HIGH): when processing client `max-stale` directives the library fails to properly validate security-zeroed cache entries, letting unauthenticated attackers retrieve cached responses belonging to other users (e.g. another user's `Set-Cookie` credentials) from a shared cache. The advisory covers all versions through 4.2.0 and no fixed release is listed. The package is transitive via `astro@7.3.2` (`bun.lock:612`, `"http-cache-semantics": "^4.2.0"`; pin at `bun.lock:900`). This deployment has no shared cache, no per-user server responses, and never loads the sole consumer module, so the published rating does not carry over to this codebase.

## Evidence

**Advisory evidence:** `CVE-2026-93748` applies to `http-cache-semantics` at installed version `4.2.0`. The advisory is fixed in `none published`.

**Transitive dependency:** introduced by the direct dependency `astro@7.3.2`.

**Dependency chain:** `astro@7.3.2 > http-cache-semantics@4.2.0`

**Usage analysis:** imported by application code; affected API usage unconfirmed. http-cache-semantics is not imported by application code; it enters only through the direct dependency `astro@7.3.2` (package.json:26; bun.lock:612 requires `"http-cache-semantics": "^4.2.0"`, pin at bun.lock:900). A full-tree dependency map over all 620 locked packages found exactly one consumer: `node_modules/astro/dist/assets/build/remote.js:1` (`import CachePolicy from "http-cache-semantics"`), used at :15 and :50-52 to build policies from the build's own request/response objects (`webToCachePolicyRequest` at :66 never sets maxStale). That module is the build-time remote-image fetcher; this project contains zero remote-image usage (`rg 'astro:assets|<Image|getImage' src/` → no hits), so the module is never loaded during `astro build`. The Ghost CMS fetch uses `@tryghost/content-api` whose only runtime dependency is axios 1.20.0 (`node_modules/@tryghost/content-api/package.json`), not http-cache-semantics. The vulnerable behavior additionally requires attacker-supplied `max-stale` request directives against a multi-user shared cache — a component that does not exist in this static nginx deployment. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

No impact demonstrated in this codebase. The vulnerable behavior would allow cross-user disclosure of cached HTTP responses (including session cookies) from a shared cache; here the only consumer is astro's build-time remote-image caching, the project uses no remote images, and the site serves identical static files to every visitor, so there are no per-user cached responses and no attacker-reachable cache query path. Risk is latent: a future feature that enables remote images or server-side/shared caching would pull this code into an active path while the version remains unfixed upstream.

## Technical Analysis

**Version verification.** `bun.lock:900` pins `http-cache-semantics@4.2.0`; the advisory states "through 4.2.0" with no fixed version, so the pin is affected. Trivy (DB refreshed 2026-10-14 at scan time) matched it from `bun.lock`.

**Source-to-sink trace (this codebase).**
- Entry point: lockfile pin `bun.lock:900`; direct dependency `astro: ^7.3.2` at `package.json:26`; astro requires `"http-cache-semantics": "^4.2.0"` (`bun.lock:612`).
- Sole consumer in the entire locked tree: `node_modules/astro/dist/assets/build/remote.js:1` — imported and used at :15/:50 to construct `new CachePolicy(webToCachePolicyRequest(req), webToCachePolicyResponse(res))` for build-time remote image fetches. The request object is generated by the build itself (`webToCachePolicyRequest({url, method, headers})` at :66); no `maxStale` option is ever passed.
- This project never exercises that module: `src/` contains no `astro:assets`, `<Image>`, or `getImage` usage, so `astro build` performs no remote image fetching.
- The Ghost content fetch (`src/lib/ghost.ts:14`) goes through `@tryghost/content-api`, whose only declared dependency is axios 1.20.0 — a separate HTTP stack not covered by this CVE.
- The deployed site is static files served by nginx: there is no application-level HTTP cache, no per-user responses, and no endpoint where an attacker can send a `max-stale` directive.

**Counterevidence pass.** Verified the consumer set exhaustively (dependency map across all 620 locked packages; only astro imports the package), confirmed the consumer module is dead code for this configuration (no remote images), and confirmed the Ghost fetch stack is independent (axios). The theoretical residual — enabling remote images later while the version stays unfixed — would still only affect the build's local image cache, not a multi-user shared cache.

**Environment caveat.** Web search was unavailable; advisory identity and the "no fixed version" status were taken from the Trivy DB refreshed on scan day plus embedded references (Red Hat CVE page, upstream issue #56, VulnCheck advisory).

## Contextual CVSS

The published 7.5 (AV:N/PR:N/C:H) assumes an internet-facing shared HTTP cache holding other users' responses (e.g. session cookies) that an unauthenticated attacker can query with `max-stale`. In this codebase no such component exists: the only consumer of http-cache-semantics in the whole 620-package tree is astro's build-time remote-image module `node_modules/astro/dist/assets/build/remote.js:1` (constructed at :15 and :50 from build-generated request/response objects with no maxStale option), that module is never loaded because the project uses no remote images (zero `astro:assets`/`<Image>`/`getImage` references under `src/`), and the Ghost content fetch goes through `@tryghost/content-api` → axios 1.20.0 (`src/lib/ghost.ts:14`), not through this cache. The deployed artifact is static files behind nginx with no per-user server responses to cache. Consequently every impact metric is N in this codebase: the vulnerable max-stale validation path exists in the build toolchain but has no attacker-reachable instance and no sensitive cached data; the advisory score is retained as the published reference only.

## Remediation

No fixed release exists upstream at scan time. Track kornelski/http-cache-semantics issue #56 and bump via `bun update http-cache-semantics` (or a root package.json `overrides` entry pinning the first fixed version) once a release lands; astro's range `^4.2.0` will accept it. Also upgrade `astro` when a release ships with the fixed dependency. As defense in depth, avoid enabling astro remote-image fetching or any server-side/shared response caching for this site without first confirming the dependency has been fixed; if remote images are ever introduced, verify no cache is shared across users.
