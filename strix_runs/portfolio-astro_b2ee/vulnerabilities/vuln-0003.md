## Description

The `bun.lock` tree pins **postcss-selector-parser 6.0.10**, affected by **CVE-2026-104844** (published advisory CVSS 5.9 MEDIUM): `splitWord()` can receive a flat selector as one word token carrying many class/ID indexes, and repeated deduplication and membership scans make parsing quadratic in the number of indexes, allowing a crafted selector to cause prolonged CPU consumption (denial of service). Versions before 7.1.6 are affected; the fix is 7.1.6. The package is a transitive, exactly-pinned dependency of **@tailwindcss/typography 0.5.20** (`bun.lock:422`, `"postcss-selector-parser": "6.0.10"`), which is a direct dependency of this project (`package.json:20`) and active via `@plugin "@tailwindcss/typography"` in `src/styles/globals.css:3`. The vulnerable parser runs on every build, but its input is entirely developer-authored CSS — no attacker-controlled data reaches it in this codebase.

## Evidence

**Advisory evidence:** `CVE-2026-104844` applies to `postcss-selector-parser` at installed version `6.0.10`. The advisory is fixed in `7.1.6`.

**Transitive dependency:** introduced by the direct dependency `@tailwindcss/typography@0.5.20`.

**Dependency chain:** `@tailwindcss/typography@0.5.20 > postcss-selector-parser@6.0.10`

**Usage analysis:** the advisory's affected API is used in application code. The vulnerable parser is loaded and executed on every build: the direct dependency `@tailwindcss/typography@0.5.20` (package.json:20, pin at bun.lock:422 with exact dependency `"postcss-selector-parser": "6.0.10"`) does `const parser = require('postcss-selector-parser')` at node_modules/@tailwindcss/typography/src/utils.js:1 and invokes it over the `.prose` selectors it generates; the plugin is activated for this project by `@plugin "@tailwindcss/typography"` at src/styles/globals.css:3. Every class/ID-bearing selector processed there flows through the advisory's `splitWord()` path. Input control was traced: the parser is fed only plugin-generated selectors plus CSS/class names from developer-authored files under `src/` scanned by Tailwind v4 source detection; Ghost CMS content is fetched into memory at build time (src/lib/ghost.ts:14-27) and rendered via `set:html` in src/pages/blog/[...slug].astro — it is never written to scanned source files, and dist/ (where built HTML lands) is gitignored (.gitignore:2) and excluded by Tailwind's source detection. No HTTP endpoint or other attacker-reachable path feeds this parser. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

Build-time denial of service on the operator's machine or CI: a single crafted CSS selector (a class or ID list with quadratic index growth) committed to a scanned source file could block `astro build` for an extended period. No confidentiality or integrity impact, and no impact on the deployed static site or its visitors — the parser never runs at request time. Reaching the input requires the ability to write to the repository (or otherwise control files Tailwind scans), which already implies the ability to break or alter the build.

## Technical Analysis

**Version verification.** `bun.lock:422` pins `@tailwindcss/typography@0.5.20` with the exact dependency `"postcss-selector-parser": "6.0.10"`, locked at `bun.lock:1072`; the advisory affects all versions before 7.1.6, so 6.0.10 is affected. Trivy (DB refreshed 2026-10-14) matched it from `bun.lock`.

**Source-to-sink trace (this codecode).**
- Entry point: direct dependency `@tailwindcss/typography: ^0.5.20` at `package.json:20` → exact transitive pin `postcss-selector-parser@6.0.10` (`bun.lock:422`, `bun.lock:1072`).
- Activation: `@plugin "@tailwindcss/typography"` at `src/styles/globals.css:3` loads the plugin into the Tailwind v4 pipeline (`@tailwindcss/vite` in `astro.config.mjs`).
- Sink: `node_modules/@tailwindcss/typography/src/utils.js:1` requires the parser and calls it over generated `.prose` selectors; the vulnerable `splitWord()` path handles every class/ID-bearing selector.
- Input provenance: selectors come from the plugin's own generated CSS plus developer-authored class names in scanned source files. Ghost content (the only conditionally attacker-controlled input per the threat model) is fetched at build time into memory (`src/lib/ghost.ts:14`) and rendered with `set:html`; it never reaches Tailwind's file scan, and `dist/` is gitignored (`.gitignore:2`) so build output is excluded from source detection.

**Counterevidence pass.** Confirmed the plugin is actually active (not vendored-unused), confirmed the parser runs on developer-controlled input only, and confirmed no scanned path can contain CMS-derived strings during a clean Docker build (the Dockerfile builds from a fresh checkout with no pre-existing dist/). The one theoretical vector — a malicious PR adding a crafted selector — requires commit access, which is a trusted position; that constraint is reflected in the contextual rating (PR:H, A:L) rather than used to dismiss the finding.

**Environment caveat.** Web search unavailable; CVE/GHSA identity, affected range, and CVSS taken from the Trivy DB refreshed on scan day.

## Contextual CVSS

The published 5.9 (AV:N/PR:N/A:H) assumes an attacker can feed crafted CSS selectors to a network-reachable service running the parser. In this codebase the parser runs only inside the operator's build: entry point is the direct dependency pin `@tailwindcss/typography: ^0.5.20` (package.json:20; bun.lock:422 pins the plugin and its exact dependency `postcss-selector-parser: 6.0.10`), activated by `@plugin "@tailwindcss/typography"` at src/styles/globals.css:3, whose `require('postcss-selector-parser')` at node_modules/@tailwindcss/typography/src/utils.js:1 parses only selectors the plugin itself generates plus CSS from developer-authored source files scanned by Tailwind v4. No network endpoint exposes the parser; Ghost CMS content fetched at build time (src/lib/ghost.ts:14) is rendered via set:html and never enters Tailwind's source scan (Tailwind v4 respects .gitignore; dist/ is gitignored). Feeding a quadratic-blowup selector would therefore require commit access to the repository — the same trusted position that could simply break the build directly — so attack vector is local, privileges required high, and the demonstrated impact is build-time CPU denial (A:L), not a service outage.

## Remediation

Override the transitive dependency to the fixed major and verify the build still passes: add a root package.json `overrides` entry pinning `postcss-selector-parser` to `^7.1.6`, run `bun install`, then `bun run build` and visually check the blog typography (the 7.x release is a major bump — selector AST API changes could affect the plugin, so a regression check of `.prose` styling is required). Alternatively, wait for or vendor a `@tailwindcss/typography` release that updates its pinned `postcss-selector-parser` dependency (currently the exact pin `6.0.10` at bun.lock:422 prevents any non-overridden upgrade). The plugin is genuinely used (src/styles/globals.css:3), so removal is not a drop-in option.
